# Deviations from the submitted design document

The design document (`Design_Document_Group_006_043_.pdf`) was reviewed against the
assignment guidelines before implementation. This table lists every place where
the implementation deliberately differs, and why. The final report's Design
section must include it, as the guidelines require.

| # | Design § | Design said | Implementation does | Why |
|---|---|---|---|---|
| 1 | 4.3, 6.1 | Client `SO_RCVTIMEO` = 15 s | Part I client: **no receive time-out**. Part II clients keep 15 s. | With the single-threaded server, queued clients wait for every earlier client. With 32 clients the later ones would time out and exit 1. |
| 2 | 3.1 | Payload over 64 KB rejected for control messages | Cap **per message type**: MANIFEST up to 64 MiB, everything else ≤ 64 KB | The MANIFEST of `cane` (4 863 files) is about 250 KB and would have been rejected. |
| 3 | 2.1, 7 | Topic array under an rwlock; a re-scan rebuilds it; sessions keep `topic_idx` | Each `topic_t` is allocated once and never moved or freed. The map is a sorted array of pointers. A re-scan only adds topics and swaps the new array in under a brief write lock. Sessions keep `topic_t*`. | A re-scan could otherwise realloc or reorder topics in use by worker threads, and with a reader-preferring rwlock the re-scan (and the 404 reply) would wait for every active transfer. |
| 4 | 1.3 | — | Output goes to `output_dir/<topic exactly as typed>/`, which is created with `mkdir -p`. On success only the topic files remain (no `.part`/`.session`). | The grader checks the directory named after the topic it passed, even when the server matched it case-insensitively. |
| 5 | 8.4 | `-Werror` in the Makefile | Shipped `make` uses `-Wall -Wextra` without `-Werror`. `make strict` adds `-Werror` and is our gate (gcc + clang). | One new warning on the grader's compiler version would otherwise mean no executables at all. |
| 6 | 6.2 | Optional byte-range split for files > 8 MB (`ftruncate` + `pwrite`) | Not implemented. Each FETCH transfers one whole file, and big files still resume by byte offset. | Pre-sizing with `ftruncate` breaks the invariant ".part size = checkpoint offset". Animals-10 files are tens of KB. |
| 7 | 4.4, 8.1 | Example "N = 1 700 chunks, roughly the size of cane"; folder `..._043_006` | That example is *gatto* (1 668 files); *cane* has 4 863. Every name uses `006_043`. | Text errors. |
| 8 | 7 | Logs written to a file | CSV logs only when `FDS_LOG` / `FDS_EVENTS` are set (plus `FDS_RUN_ID`, `FDS_CLIENT_ID`). Otherwise a summary goes to stderr. | The guidelines forbid hard-coded paths. |
| 9 | 4.1–4.3 | On a fault, the chunk that drew it is not sent at all | The cut lands at a random byte, not on a chunk boundary: the bytes before it are sent, then `shutdown`+`close`. (The per-chunk draw itself was later replaced by one draw per connection, see 28.) | The guidelines require correctness when a disconnection happens "at any point in time". Most images are under 64 KB, so without this every fault would land at offset 0 and byte-offset resume would never be exercised. Byte accounting stays exact because the server counts what `sendfile()` returned. Consequence: at p = 1 every chunk is cut, so no case can finish (as in the design). Case 2/Enhanced still move forward by a partial chunk per connection, but the last byte of a chunk is never sent, so they give up with exit 2 after max_retries attempts without progress. Effect on the design §4.4 formula for Case 1: (1−p)(1−P)/(pP) counts complete chunks only. With the prefix, each fault also sends part of a chunk (half on average), so the data transmitted lies between that value and (1−P)/(pP) chunks, which is the expected number of chunk *draws*. `tools/exp/analyze.py` reports the draws figure; its byte-overhead prediction uses the byte-exact model. |
| 10 | 6.3 | — | `TCP_NODELAY` on every data socket. `MSG_MORE` still coalesces headers with data. | Nagle + delayed ACK can stall each per-file FETCH turnaround of Enhanced by up to ~40 ms. |
| 11 | 5.5, 6.2 | Enhanced FETCH validated "with the rules of §5.5" | An Enhanced session keeps `sent_off[i]` per file. Check 5 becomes `offset == 0 or offset <= sent_off[i]`. | With K connections one (next_file, offset) pair cannot describe progress. |
| 12 | 5.3 | 256 slots, expired after 300 s | A new or adopted session takes the first usable slot in this order: a FREE slot; the oldest DONE slot; any slot idle for more than 300 s, whatever its state (an ACTIVE session idle that long has a dead connection); the oldest INTERRUPTED slot. A fresh ACTIVE slot is never evicted; if every slot is one → ERROR 503. A session announced by MANIFEST is INTERRUPTED until its first FETCH arrives. | Long experiment series must not run out of slots, and a stale or unused session must not pin a slot. |
| 13 | 6.2 | Enhanced recovery re-queues (file, offset) | Same, plus: after a client restart the queue is rebuilt from MANIFEST + files on disk (only if `.session` exists). Back-off resets after progress. FETCH is never pipelined. | Restart-safety. Unread data at close would turn the close into an RST that discards queued bytes. |
| 14 | 8.1–8.3 | `accept_loop()` and `signal_thread()` in each `server.c` | They live in the shared `server_core.c`. Each `server.c` keeps `main()` + `serve_client()`. | One implementation of the thread model for all four versions. |
| 15 | 6.5–6.7 | p ∈ {0, 5e-4, 1e-3, 2e-3, 5e-3, 1e-2}, K ∈ {2, 4, 8} | p ∈ {0, 0.1, 0.2, 0.3, 0.5, 0.7, 0.9} (p is per connection, see 28), K ∈ {1, 2, 4, 8}. Both data bytes and wire bytes are counted. A throughput-vs-overhead plot is added. | With p per connection every case finishes for p < 1, so the sweep covers the whole range. K = 1 separates parallelism from per-file FETCH cost. The guidelines ask for "throughput v/s overhead". |
| 16 | 8.2 | `tcp_connect(ip, port)` | `getaddrinfo` (IP or host name), connect time-out 10 s, listen backlog `SOMAXCONN`. | Robustness. |
| 17 | 8.2 | module names | Added `util` (argument parsing, paths, time, back-off) and `server_core`; `transfer` holds client `recv_file`/`recv_topic`. | Shared code. |
| 18 | 3.6, 7 | Back-off 50 ms doubling to 1 s between attempts | Same sequence, but the back-off counter is the number of *consecutive attempts that received no file data*. An attempt that was cut after receiving data is followed by a 50 ms wait. This applies to all Part II clients. In Case 1, `max_retries` still counts every attempt. | Back-off protects a server that is down or unreachable. After an injected fault the server is healthy, and doubling the wait would only add idle time to every completion-time measurement. |
| 19 | 5.4 | `<name>.part` holds partial data | Unchanged. **Known limitation:** Case 2 and Enhanced can only resume files whose names are at most 250 bytes long, because `<name>.part` must still fit the 255-byte file-name limit of Linux file systems. Part I and Case 1 support the full 255 bytes. | Animals-10 names are about 10–70 bytes. Supporting longer names would need a different partial-file naming scheme, at the cost of the simple ".part size = offset" rule. |
| 20 | 4.2 | Seeded generator: `srand48_r(seed ^ conn_id)` | The 48-bit `drand48_r` state is `splitmix64(splitmix64(seed) ^ conn_id)` (`seed48_r`). It is still fully repeatable for a given seed and gives each connection its own sequence. Without a seed, wall time, thread id, conn_id and monotonic time are each mixed in with the same hash (the design's plain XOR can cancel out correlated inputs). | Found in the emulated dry run. The repetitions use seeds 1001, 1002, ... (design §6.4), and with plain XOR the per-connection seeds of two repetitions overlap in 30 of 32 values. Repetitions were not independent: both Case 1 runs at p = 0.01 gave exactly 28 faults, which would understate the standard deviation in the report. |
| 21 | 6.7 | Throughput = data bytes ÷ (last connection end − first connection start) | Unchanged, but a connection's end is taken after the server has half-closed (`shutdown(SHUT_WR)`) and seen the client's own close, waiting at most 5 s in total, an absolute deadline (`drain_until_peer_closes` in `server_core.c`). | `send()`/`sendfile()` return when the kernel has *queued* the data. Ending the interval there leaves the last few MB of socket buffer outside it and inflates throughput by about 10 % at N = 1. Every client closes right after its last message, so the wait is one round trip. The 5 s cap bounds a misbehaving client (in single-threaded mode it would hold the server for at most 5 s). The final close is then a clean FIN. |
| 22 | 5.5 | Check 5 applies whenever the session id is known | A session the server *adopted* (unknown id, accepted after checks 1–4) skips check 5 permanently. Checks 1–4 still apply to every request. | The server has no record of what was sent before it adopted the id, so it has no upper bound for check 5. With Enhanced, checking anyway would wrongly reject a valid `.part` of a different file. A rejected checkpoint only causes a fresh start, never wrong data, so skipping the check is safe. |
| 23 | 1.3 | Enhanced client: `[connections] [max_retries]` | A third optional argument selects the client engine: `threads` (default) or `poll`. `io=threads` / `io=poll` are also accepted. | The guidelines allow extra optional trailing arguments with defaults. The engine choice is the "non-blocking socket" variant of design §6.1. |
| 24 | 6.7 | "Reconnects should equal the number of injected faults" (consistency check) | Holds for Case 1 and Case 2. In Enhanced, `reconnects` can be lower than the number of faults. | After a fault the worker re-queues its file. Often another worker whose connection is still open takes that file before the failed worker reconnects, and the failed worker may never need to reconnect. For Enhanced the consistency check is server data bytes = client data bytes = topic bytes × clients (no redundant bytes). |
| 25 | 3.1, 7 | Requests read with recvall() under `SO_RCVTIMEO` (30 s); payload caps per type | Servers read requests with `conn_recv_request()` (`server_core.c`). The whole request must arrive within 30 s (an absolute deadline, not per byte). Only GET, RESUME, MANIFEST_REQ and FETCH are accepted, with a payload ≤ 512 bytes, checked before anything is allocated. | Found in the robustness review. A peer sending one byte every 29 s could hold a thread for days, and in single mode the whole server. A client could also announce a 64 MiB "MANIFEST" and make the server buffer it (3 such connections added 190 MB of memory). |
| 26 | 1.3, 7 | Part I client: any error → exit 1 | ERROR 503 (thread limit reached) is retried with the usual back-off, up to 100 times. Every other error is still fatal. | 503 means "busy", not a failed transfer. With 300 simultaneous clients, 44 used to exit 1. Part II clients already retried 503. |
| 27 | 6.2 | Enhanced: fresh start | On a fresh start (no `.session`) the client deletes every manifest file and every `*.part` in the output folder BEFORE writing `.session`. A FETCH connection that ends before the topic is fully sent sets the session INTERRUPTED. | Found in the robustness review. Writing `.session` first meant that killing the client within its first second made the next run trust stale same-size files: 73 files were corrupted in the test. The server-side change keeps an abandoned session from pinning a slot ACTIVE for 300 s; 256 of them used to fill the table. |
| 28 | 4.1–4.4 | One independent fault draw before every 64 KB chunk: p = probability of a cut per chunk | **One decision per connection.** When the connection's first data request is accepted, one draw decides whether the connection will be cut (probability p); a second draw picks the cut byte uniformly in that request's data: the whole topic (Case 1 GET), the rest of the topic from the checkpoint (Case 2 GET/RESUME), the rest of the requested file (Enhanced, first FETCH). The server sends the bytes before the cut, then `shutdown`+`close`. A 0-byte request leaves the decision to the next one. `fault_plan()` in `common/fault.c`. | The guidelines say p "specifies how frequently the client-server session is interrupted". With a per-chunk p, a Case 1 attempt survives with probability (1−p)^N: on a real topic (gatto, about 1 800 chunks) Case 1 gave up (exit 2) at every p ≥ 0.01, so an automated test with a usual p such as 0.1 would have failed Case 1. Now an attempt survives with probability 1−p whatever the topic size: Case 1 needs 1/(1−p) attempts on average and wastes about half the topic per cut; Case 2 and Enhanced still lose nothing. p = 1 cuts every connection before the last byte, so nothing finishes. In Enhanced each of the K connections is cut with probability p (in its first file). |
