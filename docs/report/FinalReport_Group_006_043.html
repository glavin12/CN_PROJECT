1. Overview and command-line interface

A server maps each topic (one sub-folder of topics_root_dir, here the ten animal folders of the Animals-10 dataset) to the files in it. A client names a topic and receives every file of that topic into output_dir/<topic>/. The project is written in C (gnu11) with POSIX threads and TCP/IPv4 sockets on Linux and is delivered as four self-contained versions:

FolderVersionBehaviour after a cut connection
Part1/Plain service, single or multi (default) serverno faults injected
Part2_Case1/Fault injection, no session managementthe client reconnects and the whole topic is sent again
Part2_Case2/Fault injection + session managementthe client resumes from a checkpoint (file index, byte offset)
Part2_Case2_Enhanced/Case 2 + K parallel TCP connections, blocking or non-blocking clientthe failed file is re-queued at its offset and fetched by any connection

Every folder builds exactly two executables, server and client, with make and no warnings. Nothing is hard-coded: port, path and address come only from the command line.

Part I server:        ./server <port> <topics_root_dir> [single|multi]
Part II server:       ./server <port> <topics_root_dir> <failure_probability> [seed]
Client (all cases):   ./client <server_ip> <server_port> <topic> <output_dir>
  Case 1 extra:       [max_retries=100]
  Case 2 extra:       [max_retries=20]
  Enhanced extra:     [connections=4] [max_retries=20] [threads|poll]
Exit codes:           0 success, 1 fatal/usage error, 2 gave up after max_retries

On success the topic folder holds exactly the topic's files; partial files (.part) and the session record (.session) exist only while a transfer is unfinished.

2. Part I: implementation

2.1 Server data structures: mapping topics to directories

At start-up the server reads topics_root_dir with opendir()/readdir(). Every sub-folder becomes a topic_t whose key is the folder name and whose value is the folder's realpath(). Each folder is scanned once; its regular files are stored with their sizes and sorted by name, so a file index always denotes the same file (the Case 2 checkpoints rely on this). Requests are then answered without touching the directory again.

typedef struct { char name[NAME_MAX+1]; uint64_t size; } file_entry_t;
typedef struct {
    char key[64];             /* topic key = folder name, e.g. "gatto"   */
    char abs_path[PATH_MAX];  /* realpath() of the folder (the map value) */
    file_entry_t *files;      /* sorted by name                           */
    uint32_t n_files;  uint64_t total_bytes;
} topic_t;
/* topic_map_t: sorted array of topic_t* + pthread_rwlock_t (re-scan only) */
  • Lookup: bsearch() on the sorted key array (exact match first, then a case-insensitive match, so Cane finds cane). An unknown topic gets ERROR 404.
  • Concurrency: after start-up the map is read-only for worker threads. Each topic_t is allocated once and never moved or freed; a re-scan for newly created topic folders (at most once per second, triggered by an unknown topic) only adds topics and swaps a new pointer array in under a short write lock.

For the Animals-10 dataset the map holds 10 topics with 26 179 files and 614 MB in total (e.g. cane 4 863 files / 60.7 MB, elefante 1 446 files / 58.5 MB, gatto 1 668 files / 151.1 MB).

2.2 Client-server message format

TCP is a byte stream, so every message is framed by a fixed 16-byte header followed by payload_len payload bytes. All integers are packed field by field in network byte order; structures are never sent raw. All socket I/O goes through sendall()/recvall() loops that handle short transfers and EINTR and use MSG_NOSIGNAL.

Part I exchange. The client sends GET <topic>. The server replies TOPIC_BEGIN, then for every file FILE_HDR + raw bytes + FILE_END, and finally TOPIC_END with the totals, which the client checks before exiting 0. File data is sent with zero-copy sendfile() in 64 KB chunks; headers are sent with MSG_MORE so the kernel coalesces them with the following data. The client rejects any file name containing /, .., a leading dot or control characters. Part I and Case 1 write each file directly under its final name, opened with O_TRUNC, so a restarted Case 1 attempt overwrites the earlier partial data.

Robustness. A request must arrive completely within an absolute 30 s deadline, only the four request types are accepted and their payload is limited to 512 bytes before anything is allocated; a malformed request gets ERROR 400. Server sockets use 30 s send/receive time-outs.

2.3 Single-threaded and multi-threaded server

Both modes share one accept loop (server_core.c); only the scheduling differs:

  • single: the accept loop calls serve_client() directly. Clients are served strictly one after another; the others wait in the kernel's listen backlog (SOMAXCONN).
  • multi: each accepted connection is handed to a new detached POSIX thread that runs serve_client(), so clients are served concurrently. At most 256 worker threads run at once; a connection beyond that gets ERROR 503 and the client retries with back-off. Shared state (thread counter, statistics, topic map) is protected by mutexes / the rwlock.
  • Shutdown: a dedicated signal thread waits for SIGINT/SIGTERM with sigwait(), stops accepting, gives active transfers up to 5 s, prints a summary and exits 0. SIGPIPE is ignored.

Timing and byte counting (for the measurements). Every connection records its start and end with clock_gettime(CLOCK_MONOTONIC) and counts the data bytes actually returned by sendfile(). A connection's end is taken after the server has half-closed and seen the client's close, so the interval includes the data still queued in the socket buffer.

3. Part II: implementation

All Part II cases use the multi-threaded server of Part I (one thread per client connection) with fault injection added.

3.1 Fault injection: when and how the failure decision is made

  • Meaning of p. <failure_probability> p is the probability that a connection is interrupted during its file transfer. Each connection is cut with probability p, independently of the others and of the topic size.
  • When. Once per connection, at the moment the server has accepted the connection's first data request and knows how many file bytes it will send for it: the whole topic for a Case 1 GET, the rest of the topic from the checkpoint for a Case 2 GET/RESUME, the rest of the requested file for the first FETCH of an Enhanced connection. Control messages never get a decision, so every fault interrupts file data.
  • How. Every connection owns a drand48_r generator (thread-safe, no global state) seeded with a hash of (seed, conn_id); the optional [seed] argument makes runs repeatable. One draw r ∈ [0,1) decides: cut iff r < p. If so, a second draw picks the cut byte uniformly among the request's data bytes.
  • Interruption. Before each 64 KB chunk the send loop checks whether the cut byte falls inside it. If so it sends only the bytes before the cut, logs a FAULT event (connection, file, offset), then calls shutdown() and close(). The client therefore sees the connection die at an arbitrary byte, not only at file or chunk boundaries. Only that connection ends; the server keeps serving all others.
  • Expected effect. An attempt survives with probability 1−p. Case 1 needs on average 1/(1−p) attempts and each cut wastes on average half of the topic, so the expected redundant fraction is 0.5·p/(1−p). Case 2 and Enhanced re-send nothing. p = 1 cuts every connection, so no transfer can finish (clients exit 2).

3.2 Case 1: no session management

Case 1 uses the Part I messages. Neither side keeps transfer state. When the connection is lost before TOPIC_END (recv() returns 0, ECONNRESET or the 15 s receive time-out), the client waits (50 ms after an attempt that received data; 50 ms doubling up to 1 s after attempts that received nothing), reconnects and sends GET again. The whole topic is re-sent and every file is rewritten from byte 0. After max_retries attempts (default 100) the client exits with status 2.

3.3 Case 2: session management and checkpoints

A checkpoint is the tuple (session id, topic, file index, file name, byte offset). The client is authoritative for the offset, because only it knows which bytes are on its disk; the server keeps a session record and validates every checkpoint before resuming.

PhaseClient → ServerServer → Client
1. StartGET <topic>TOPIC_BEGIN(random 16-byte session id from getrandom(), counts), then files
2. Completion—TOPIC_END; session marked DONE
3. Failureconnection lostfault injected: shutdown + close; session INTERRUPTED
4. ResumptionRESUME(session id, file index, offset, topic, name)RESUME_OK(index, offset), FILE_HDR with start_offset = offset, the remaining bytes and files, TOPIC_END
5. Invalid checkpointRESUMERESUME_REJECT(reason); the client discards partial data and restarts with GET

Stored by the client. The file in progress is written to <name>.part; its size is the byte offset, so the checkpoint is updated by every write() at no extra cost and always matches the data on disk. On FILE_END the file is renamed to its final name. A small text record .session (session id, topic, file index, file name) is written atomically (temporary file + rename()) at TOPIC_BEGIN and at every FILE_HDR, and deleted after TOPIC_END. Because the checkpoint lives on disk, even a restarted client process resumes.

Stored by the server. A table of 256 session slots protected by one mutex: session id, topic, index of the file being sent, bytes of that file already sent, total bytes sent, reconnect count, state (ACTIVE / INTERRUPTED / DONE) and last-seen time (monotonic). The record is updated after every chunk sent. Idle slots expire after 300 s and are reused.

Validation of a RESUME (a failed check gives RESUME_REJECT with that number): (1) the topic exists; (2) file_index < number of files; (3) the name equals the file at that index (detects a changed directory); (4) offset ≤ file size; (5) for a known session, the checkpoint is not ahead of what the server has sent. If all checks pass, the server sends only bytes [offset, size) of that file with sendfile() from that offset, then the remaining files. No byte that was already stored is sent again, which the measurements confirm (0 redundant bytes).

3.4 Case 2 Enhanced: performance enhancements

Parallel TCP connections. The client first opens one short connection, sends MANIFEST_REQ(topic, K) and receives the MANIFEST (session id and the size and name of every file). It then opens K worker connections (default 4, range 1–16).

  • Work split: a dynamic, file-level work queue protected by a mutex holds every file index. Each worker takes the next index and sends FETCH(session id, index, offset, topic, name); the reply is FILE_HDR + data + FILE_END. Faster connections take more files, which balances the load automatically.
  • Reassembly: a file is owned by exactly one worker at a time and written to its own .part file, renamed on FILE_END. Files are independent, so no byte-stream reassembly across connections is needed.
  • Recovery: when a worker's connection fails, it puts its file back into the queue with the offset reached (the .part size) and reconnects; any worker may continue that file with FETCH from that offset. The other K−1 connections are unaffected. The server keeps, per session, the bytes sent of every file and validates each FETCH like a RESUME.
  • Completion: when the queue is empty and all workers are idle (counter + condition variable), the client deletes .session and exits 0.

Socket mode. Two client engines are implemented and measured: threads (default: one thread per connection with blocking sockets) and poll (a single thread drives all K sockets with O_NONBLOCK and poll(), treating EAGAIN as "retry when ready").

Other enhancements (all versions): zero-copy sendfile(); cached, pre-sorted file lists (no directory scan per request); MSG_MORE header coalescing; TCP_NODELAY on data sockets so the per-file FETCH round trip is not delayed by Nagle + delayed ACK; 64 KB I/O chunks; optional socket buffer sizes via FDS_SNDBUF/FDS_RCVBUF (measured in §7).

4. Experimental setup and metrics

4.1 Testbed

The experiments use three hosts: the server S and two client hosts A and B. Each host has its own Linux network stack (network namespace) and is connected to a software switch (Linux bridge) by a 1 Gbit/s link (tbf) with 0.1 ms one-way delay (netem) and the fq_codel queue discipline. The hosts are emulated on one machine (Intel Core i5-13450HX, 16 logical CPUs, Fedora Linux, kernel 7.2.11, gcc 16.2.1). The measured link capacity is 957 Mbit/s for one TCP flow and 2 × 478 Mbit/s when two flows share S's uplink, so S's 1 Gbit/s uplink is the shared bottleneck for all clients. Topics are read from S's local disk; every client writes to its own directory on local disk. The full Animals-10 dataset (10 topics, 26 179 files, 614 MB) is served.

4.2 Procedure

  • A controller script starts the server on S, then starts all clients of a run at the same moment (split evenly over A and B), waits for them, checks every client's output against the topic (file count and bytes) and stops the server with SIGINT.
  • Every configuration: 1 warm-up run (discarded) + 5 measured repetitions; values are reported as mean ± sample standard deviation.
  • Part II repetition r uses the fixed seed 1000 + r for every case, so Case 1, Case 2 and Enhanced see the same fault decisions per connection id.
  • Raw logs: the server writes one CSV row per connection plus one row per event (FAULT, RESUME, ...), each client one row per run (FDS_LOG, FDS_EVENTS). All raw CSV files are in Results/raw/; the summary tables and graphs are computed from them by tools/exp/analyze.py and tools/exp/plot.py.
  • In total 412 runs were executed (72 warm-up, 340 measured). All 340 measured runs completed and passed the output check except one Case 2 run at p = 0.9, in which one of the four clients gave up (§6.4).

Analysis

  • Aggregate throughput is the same for both servers and every N: 119.2 MB/s (954 Mbit/s). That is the capacity of S's 1 Gbit/s link minus TCP/IP header overhead. Already one client saturates the link, because the server sends with zero-copy sendfile() and its CPU is never the bottleneck. Adding threads cannot raise the rate of a link that is already full, so the throughput curve is flat.
  • The servers differ in how the link is shared. Let t = T/R = 58.5 MB / 119.2 MB/s = 0.491 s be the time to send one topic. The multi-threaded server serves all N clients concurrently; they share the bandwidth fairly and all finish together at ≈ N·t (15.7 s for N = 32). The single-threaded server serves them one after another: client i finishes at i·t, so the mean is (N+1)/2·t (8.10 s for N = 32) while the last client still finishes at N·t. The measurements match both formulas exactly.
  • For equal requests on a shared bottleneck, first-come-first-served (single) therefore gives a lower mean completion time, whereas the multi-threaded server gives every client steady progress from the start (per-client goodput R/N) and the same worst-case completion time.
  • The multi-threaded server is the right design whenever the bottleneck is per connection rather than the shared link: a slow or distant client (high round-trip time, Wi-Fi), very different topic sizes (a small request is not stuck behind a large one) or a stalled client, which would block the single-threaded server for every other client until its time-out. Part II therefore builds on the multi-threaded server.

6.1 Total, useful and redundant bytes

  • Case 2 never sends a byte twice. At every p the server sent exactly the useful 604.6 MB (overhead 0 %), with on average 36 faults per run at p = 0.9: each RESUME continues from the byte offset the client has stored.
  • Case 1 re-sends the whole topic after every cut. Its redundant bytes grow from 49.7 MB (8.2 %) at p = 0.2 to 3 317 MB (549 %) at p = 0.9, i.e. the server transmitted 6.5 times the useful data. The model of §3.1 predicts 0.5·p/(1−p): 12.5 %, 21.4 %, 50 %, 117 % and 450 % for p = 0.2 … 0.9; the measurements (8.2, 19.3, 45.2, 106, 549 %) follow it closely (Figure 4). The large standard deviations (e.g. 45 ± 34 % at p = 0.5) are inherent: each cut wastes a uniformly random fraction of the topic and a run has only a few cuts.
  • At p = 0.1 no connection was cut in any of the 5 repetitions (prediction: 0.4 faults per run), which is why both cases equal p = 0 there.
  • The measured number of faults agrees with the prediction (e.g. Case 1: 3.6 vs 4.0 at p = 0.5, 8.6 vs 9.3 at p = 0.7), which confirms that p behaves as specified.

6.2 Completion time and throughput vs overhead

  • Aggregate throughput hardly changes with p (Case 1: 119.5 → 115.9 MB/s): the link stays busy, but in Case 1 it is busy with redundant data. Goodput shows the real cost: Case 1 falls from 119.5 to 85.9 MB/s at p = 0.5 and to 22.3 MB/s at p = 0.9, roughly throughput ÷ (1 + overhead), as Figure 6 shows. Completion time rises accordingly from 5.06 s to 6.03 s (p = 0.5) and 19.4 s (p = 0.9).
  • Case 2 keeps goodput and completion time at the fault-free level up to p = 0.7 (116.7–119.5 MB/s, 5.03–5.06 s). Each fault only costs a reconnection (a 50 ms back-off and one round trip).

6.3 Comparison with Part I

With p = 0 every Part II version reaches the Part I multi-threaded result with the same topic and 4 clients (119.5 MB/s, 5.06 s): Case 1 and Case 2 119.5 MB/s, Enhanced 119.2–119.3 MB/s, i.e. 100 % of Part I. Fault injection and session bookkeeping therefore cost nothing measurable when no fault occurs. The protocol overhead on the wire (headers and control messages) is 0.091 % of the data for Part I, Case 1 and Case 2.

6.4 Case 2 at p = 0.9: the tail effect

At p = 0.9 Case 2's mean goodput drops to 73.6 ± 39 MB/s and one client of one run gave up. The per-client logs show why. Most clients still finished in 4.9–5.8 s, but clients that needed 25–47 attempts took 13–22 s. Each cut happens at a uniformly random byte of the connection's remaining data, so after a few cuts the remaining part of the topic becomes small, and a cut of a small remainder delivers few or no new bytes. Attempts without new data double the back-off up to 1 s. The client that gave up had received all but the very last byte (151 144 281 of 151 144 282 bytes): with one byte left, every cut falls on byte 0, and 20 such attempts in a row (probability 0.920 ≈ 12 %) exhaust max_retries. This is a consequence of the extreme fault rate combined with the retry limit, not data loss: the received data was correct. Case 2 Enhanced does not show the effect (§7).

Measured improvement and justification

  • Under faults, Enhanced is clearly better. At p = 0.9, K = 4 delivers 118.5 MB/s goodput against 73.6 MB/s for Case 2 (+61 %) and 22.3 MB/s for Case 1 (5.3×), with mean completion 4.88 s against 6.46 s and 19.39 s, no redundant byte and no client giving up. With K = 8 goodput stays at 119.1 MB/s even at p = 0.9, i.e. at the fault-free level. Why: a connection is cut at most once, inside the first file it fetches, so every connection that survives its first file is never interrupted again. When a connection fails, its file goes back into the queue with its offset and is usually taken by one of the other K−1 connections that are still open, so the tail of tiny, repeatedly cut remainders seen in Case 2 (§6.4) does not occur, and the link keeps carrying data during reconnections.
  • Without faults the improvement is zero on this network (119.2–119.3 MB/s for all K, equal to Part I). One TCP connection already fills the 1 Gbit/s link: the bandwidth-delay product is only 1 Gbit/s × 0.2 ms ≈ 25 KB, far below the TCP window, and the extra per-file FETCH round trip (0.2 ms) is negligible. Parallel connections help when a single connection cannot fill the path (high RTT or packet loss, e.g. Wi-Fi or a WAN); here the shared link is the limit, and more connections only divide it.
  • Blocking threads vs non-blocking poll: identical performance (Figure 8; 118.5 MB/s at p = 0.9 for both). With K = 4 sockets the cost of threads is negligible; the poll engine reaches the same result with a single thread, i.e. fewer resources and no locking between workers, and would scale better to many connections.
  • Socket buffers: 64 KB, 256 KB, 1 MB, 4 MB and the kernel default all give 119.2–119.5 MB/s for Case 2 and Enhanced (Figure 9). Since the bandwidth-delay product is about 25 KB, even 64 KB buffers are large enough; the default (autotuning) is kept.
  • Cost: Enhanced sends one FETCH request per file, raising the wire overhead from 0.091 % to 0.129 % of the data; no data byte is ever sent twice.
  • The mean completion time of Enhanced at high p (4.4–4.9 s) is slightly below the fault-free 5.05 s because the four clients no longer share the link exactly equally, so some finish earlier; the time until the last client finishes is unchanged (aggregate throughput 115–119 MB/s).

8. Deviations from the design document

The implementation follows the submitted design document except at the following reviewed points.

#Design saidImplementation does, and why
1Client receive time-out 15 sPart I client has none (Part II clients keep 15 s): with the single-threaded server, queued clients legitimately wait for all earlier clients.

9. Conclusions

  • All four versions transfer every topic correctly; every measured run's output was verified (340 runs, one Case 2 client gave up at p = 0.9 after receiving all but the last byte).
  • Part I: on a 1 Gbit/s network a single connection with sendfile() already saturates the server's link (119 MB/s), so the single- and multi-threaded servers reach the same aggregate rate. The multi-threaded server shares the link fairly between concurrent clients, whereas the single-threaded server serves them in order (lower mean but equal worst-case completion time); multi-threading matters when connections, not the link, are the bottleneck.
  • Case 1 vs Case 2: without session management the redundant data grows as 0.5·p/(1−p) of the topic (549 % at p = 0.9) and goodput falls from 119.5 to 22.3 MB/s. With session management no byte is sent twice at any p and goodput stays at the fault-free level up to p = 0.7.
  • Case 2 Enhanced: parallel connections with a shared work queue keep goodput at 115–119 MB/s and completion near 5 s even at p = 0.9 (+61 % over Case 2, 5.3× Case 1). Without faults, parallel connections, the non-blocking engine and larger socket buffers give no gain on this low-latency network because the link itself is the limit.
