1     Overview, assumptions and command-line interface

The system is a TCP file server. It keeps a set of topics, one per sub-folder of the Animals-10
dataset (cane, cavallo, elefante, farfalla, gallina, gatto, mucca, pecora, ragno, scoiattolo). A
client sends GET <topic>. The server sends every file in that topic’s directory, and the client
writes them into output_dir/<topic>/. We implement four versions. Each one builds on the
previous one and uses the same message format.

1.2    Assumptions

    • Linux lab machines with gcc and glibc, TCP over IPv4, and a switched LAN. One machine
      runs the server and the other two run multiple clients each.
    • topics_root_dir contains one sub-folder per topic, and the folder name is the topic key.
      Regular files directly inside a topic folder are served. Hidden files and nested sub-folders
      are ignored.
    • No path, port or IP address is hard-coded. All of them come from the command line.

2     Server data structures: mapping topics to directories

that directory’s file list, sorted by name. The map is built once at startup from topics_root_

same file, which the Case 2 checkpoints rely on.

2.1     Construction, lookup and concurrency

    • Construction: the server reads topics_root_dir with opendir()/readdir(). Every
      sub-folder (checked with stat() and S_ISDIR) becomes a topic_t whose value is its
      realpath(). Each topic folder is scanned once. Regular files are stored with their sizes
      and sorted by name, and the topic array is sorted by key.
    • Lookup: topic_find(map, key) first tries an exact, case-sensitive bsearch(). If that
      fails it tries a case-insensitive match, because the assignment’s table writes "Cane" while
      the folder is "cane". An unknown topic gets ERROR 404.
    • Concurrency: after startup the map is only read, so worker threads use it without con-
      tention. They take a read lock on the pthread_rwlock_t. The write lock is taken only
      when the map is re-scanned to add a newly created topic folder (§7).


3      Client–server message formats

TCP delivers a byte stream without message boundaries, so every message is framed with a
fixed-size header that carries its type and its payload length. The receiver reads exactly 16
header bytes, then exactly payload_len bytes. All four versions share this header. Each later
version only adds message types. §3.1–3.3 define the formats and §3.5–3.8 give the exchange for
each case.




                                                                 6
3.1      Common framing header (16 bytes)

                           Every message = 16-byte header + payload_len bytes of payload

        magic         ver       type             reserved                                        payload_len
        0x5446         1    msg type           0 (future flags)                                 bytes that follow

  0               2         3          4                                 8                                                  16
                                           byte offset (all integers big-endian / network byte order)



                                Figure 2: Header used by every message in every part.

      • All integers are sent in network byte order (htons, htonl, htobe64) and converted back on
        receipt. Structures are never sent raw. Each field is packed into a byte buffer individually,
        which avoids problems with compiler padding and byte order.
      • The receiver rejects a header whose magic or version is wrong, or whose payload_len
        exceeds 64 KB for a control message. It sends ERROR 400 where possible and closes the
        connection.
      • Every read uses recvall() and every write uses sendall(). These loops continue until the
        full length is transferred and retry on EINTR. recv() == 0 before a message is complete
        means the peer closed the connection, which is treated as a connection failure.

3.4   Error handling common to all cases

   • Unknown topic: the server replies ERROR 404 and closes. The client prints the message
     and exits with status 1.
   • Malformed header or payload: ERROR 400 and close. An unreadable file gives ERROR 500,
     and the thread limit gives ERROR 503.
   • The client rejects any server-supplied file name containing ’/’, ’..’, a leading ’.’ or control
     characters (§7).

4     Fault injection mechanism

The server interrupts active connections at random, and the <failure probability> argument
p controls how often. p is the probability that the connection fails before any given
64 KB chunk of file data. Every chunk gets its own independent random decision, so p is a
per-64-KB-chunk fault probability. It is not a per-connection or per-session probability.


4.1   When the failure decision is made

The decision is made inside the server worker’s file-send loop, immediately before every 64
KB chunk of file data is sent. The last chunk of a file may be smaller than 64 KB, and a
0-byte file has no chunk and therefore no draw. Headers and control messages (TOPIC_BEGIN,
FILE_HDR, FILE_END, TOPIC_END, RESUME_OK, MANIFEST) are never preceded by
a draw, so every injected failure happens during a file transfer.
The same rule applies in every Part II case. In Case 1 and Case 2 the connection’s worker thread
draws before each chunk of the topic. In Case 2 Enhanced each of the K connections is served
by its own thread, which draws before each chunk it sends. A reconnection is a new connection,
and its chunks are drawn for in the same way.


4.2   How the failure decision is made

/* per - connection state , owned by exactly one worker thread */
struct drand48_data rng ;        /* srand48_r ( seed ^ conn_id , & rng ) when the connection starts ;
                                    without a [ seed ] argument : time ^ thread id ^ conn_id        */

/* file - send loop inside send_file_range () */
while ( off < file_size ) {
    size_t n = MIN ( CHUNK_SIZE /* 65536 */ , file_size - off );
    double r ;
    drand48_r (& c - > rng , & r );              /* one independent draw per 64 KB chunk           */
    if ( r < c - > p ) {                         /* fault triggered                                */
           log_fault (c , file_idx , off , chunk_idx );
           shutdown (c - > fd , SHUT_RDWR );
           close (c - > fd );
           return FAULT_INJECTED ;               /* worker thread ends ; server keeps running      */
    }
    send_chunk (c , in_fd , & off , n );         /* sendfile () loop , advances off by n           */
    c - > bytes_sent += n ; chunk_idx ++;
    session_update (c , file_idx , off );        /* Case 2 and Enhanced only                       */
}


    • Thread-safe random numbers: each worker thread owns its own struct drand48_data
      and calls drand48_r(), which returns a uniform value in [0, 1). The functions rand() and
      drand48() keep hidden global state and are not thread-safe.
    • Seeds: conn_id is a server-wide counter incremented for every accepted connection. With
      the optional [seed] argument the generator is seeded with seed ˆ conn_id, so a run can
      be repeated with the same sequence of draws per connection. Without it, time ˆ thread
      id ˆ conn_id is used.

4.3   How the connection is interrupted

   • When a draw is below p, the chunk that drew it is not sent. The server writes a FAULT log
     record (connection id, session id, topic, file index, offset, chunk index, data bytes sent on
     the connection). It then calls shutdown(fd, SHUT_RDWR) followed by close(fd), updates
     the statistics and ends the worker thread. The server process keeps running and continues
     to accept clients.
   • Data already sent before the fault is still delivered, followed by end-of-stream. The client
     detects the failure when recv() returns 0 or fails with ECONNRESET before the expected
     end of the file or topic. A receive time-out (SO_RCVTIMEO, 15 s) is treated the same way.
   • Because faults occur only between chunks, the client’s .part size after a fault is normally
     a multiple of 64 KB: 0 if the fault came before the file’s first chunk. The resume protocol
     does not rely on this.

 Case                  Effect of a fault and recovery
 Case 1                The client reconnects after back-off, sends GET again, and the whole topic is
                       re-sent from its first chunk, each chunk with a new draw.
 Case 2                The client reconnects and sends RESUME with offset = size of its .part file
                       (§5). Only the remaining chunks are sent, each with a new draw.
 Case 2 Enhanced       Only the failed connection closes. Its worker re-queues (file index, .part
                       size), reconnects and FETCHes from that offset. The other K − 1
                       connections continue. Because p is per chunk, the probability of a fault per
                       64 KB sent is the same as in Case 1 and Case 2.

   • p = 0: no draw can trigger a fault, and the behaviour is identical to Part I.
   • p = 1: every draw triggers a fault, so no data chunk is ever sent and no case can complete.
     Case 1 stops after max_retries attempts (default 100). Case 2 and Enhanced stop after
     max_retries consecutive attempts without progress (default 20). All exit with status 2.
   • Retry counting: in Case 1 max_retries counts every attempt. In Case 2 and Enhanced
     it counts only consecutive attempts in which no new chunk was stored, so a transfer that
     keeps making progress is never abandoned.

5     Session management protocol (Case 2)

Session management lets a transfer continue from its last checkpoint after a failure. A check-
point is the tuple (session id, topic, file index, file name, byte offset). The client is authori-
tative for the checkpoint, because only the client knows which bytes were actually stored. The
server keeps a session record and uses it to validate each checkpoint before resuming.

5.6    Checkpoint update frequency

The byte offset changes with every chunk the client writes, because it is the size of the .part
file. The .session record changes once per file. The server’s copy is updated after every chunk
sent. The client’s checkpoint therefore always matches the data on its disk, and saving it adds
no extra I/O. Because the record is on disk, a transfer can also resume after the client program
itself is restarted.
Checkpoint ownership trade-off. The table compares the three options for where the check-
point is kept.

                          state                                     bytes reached client disk
 Client only              Client knows exactly what is stored       Server cannot independently validate
                                                                    the checkpoint
 Both — chosen            Client provides authoritative             Slightly more state/synchronization
                          stored-byte offset; server validates it


Chosen approach: Both sides maintain checkpoint information, with the client authoritative
for the stored byte offset and the server validating the checkpoint before resuming.

6.1    Socket mode

   • Main implementation: blocking sockets with one thread per connection. Part
     II requires one thread per client, and blocking calls give the simplest correct code. Send
     and receive time-outs (SO_SNDTIMEO/SO_RCVTIMEO, 30 s on the server, 15 s on the client)
     stop an unresponsive peer from blocking a thread forever.
   • Measured variant: non-blocking client. A single thread drives all K sockets with
     O_NONBLOCK and poll(), treating EAGAIN/EWOULDBLOCK as "retry when ready". It will be
     compared with the threaded client. epoll was considered but only pays off with hundreds
     of sockets, and here K ≤ 16.

6.3   Other enhancements (all parts where applicable)

   • Zero-copy transfer: sendfile() moves file data from the page cache to the socket
     without copying through user space. It also starts at an explicit offset, which the resume
     logic uses. A read() + sendall() loop is the fallback.
   • Cached file lists (§2): no directory scan or stat() per request.
   • Fewer small packets: headers are sent with MSG_MORE so the kernel coalesces them with
     the following file data.
   • 64 KB I/O chunks on both sides. The client writes directly from its receive buffer to
     the output file.
   • TCP buffer sizing (optional / stretch experiment): As a stretch experiment, SO_
     SNDBUF and SO_RCVBUF may be varied to determine whether larger socket buffers improve
     throughput on the lab network. The default socket-buffer configuration will be retained
     for the main experiments.
