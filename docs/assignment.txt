Part – 1 Basic Topic Based File Distribution

In the part -1, aim is to implement a topic-based file distribution system where the server maintains
a set of topics, each mapped to a directory containing multiple files on the topic. Clients request a
topic (see dataset below), and the server responds by sending all files belonging to that topic. The
server is to be implemented in both single-threaded and multi-threaded modes to study their effect
on throughput.

It is expected that you already know multi-threaded application design which is required for
implementing multi-threaded servers. If required, please review the POSIX pthread library
specification (https://pubs.opengroup.org/onlinepubs/9799919799/) and refer to tutorials such as
LLNL POSIX Threads Guide for programming examples (https://hpc-tutorials.llnl.gov/posix/).

 PART II: Fault-Tolerant File Transfer (Handling Disconnection and Resume over the Multi-
                                     threaded Server)

Building on the multi-threaded server from Part I, this part requires the server and client to remain
correct and make forward progress even when a disconnection occurs at any point in time during
the transfer.

Fault injection: the server shall probabilistically terminate/interrupt an active client connection
during file transfer. The probability of failure shall be controlled by the <failure probability>
command-line argument provided to the server. The implementation should document when and
how the failure decision is made.

All cases below must run on the multi-threaded server, with one thread serving each client.

   •   Case 1: No Session Management. No metadata about an in-progress transfer is retained by
       either side. After a failure, the transfer restarts from the beginning.
   •   Case 2: With Session Management. Client and server maintain some state so that after a
       failure, the transfer resumes from the previous checkpoint instead of restarting from the
       beginning.
       ◦ Session management means the client and server keep track of an in-progress transfer
           instead of forgetting everything the moment a connection drops.
       ◦ A checkpoint is a small saved record of progress - typically the topic, the current file
           name, and the byte offset already sent/received for that file.
       ◦ This checkpoint state is updated periodically as the transfer proceeds (e.g., after every
           file, or after every few KB), on the server, the client, or both.
       ◦ When the client reconnects after a failure, it reports its last known checkpoint; the server
           validates it and resumes sending from that byte offset instead of from the first byte of the
           topic.
       ◦ No data that was already successfully transferred and recorded needs to be sent again.
   •   Measure and compare performance of your implementation with and without session
       management by varying the fault injection rate. Compare the total bytes transmitted, useful
       bytes successfully delivered, redundant bytes retransmitted, completion time, throughput v/s
       overhead, and compare your results with Part 1 values.

To improve performance further, you may consider the following performance enhancements in
the Part-II – Case 2. We call it as Part-II – Case 2 – Enhanced
    • Socket mode: you may use either blocking or non-blocking sockets. In the Blocking sockets,
        the socket API calls (accept/send/recv) pause the calling thread until the operation
        completes, so the thread does nothing else while it waits. In the Non-blocking sockets, the
        socket APIs returns immediately even if it cannot complete right away (e.g., no data yet).
    • Parallel TCP Connections: Instead of a single connection, the transfer for one topic uses
        multiple simultaneous TCP connections between client and server. The design and
        implementation approach (how many connections are used, how work is split across
        connections, how data is reassembled, how a failed connection is recovered) is left to you -
        document and justify whatever choices you make.
    • Report the performance enhancements used. Measure and report the performance
        improvement. Support your claims with appropriate justification and result analysis.

Standard CLI Interface (Required So Your Submission Can Be Auto-Tested)
The grading script builds and runs your programs against a reference dataset it supplies, so nothing
in your server or client may hard code a file path, port number, or IP address – every one of these
must come from a command-line argument, exactly as follows. Deviating from this interface (extra
required arguments, interactive prompts, hard coded paths/ports, differently named executables)
will make the automated check fail for that case, regardless of whether your code works when you
run it manually.

   •   Required invocation of server program
       ◦ for Part 1: ./server <port> <topics_root_dir>
       ◦ for Part 2 all cases: ./server <port> <topics_root_dir> <failure probability>
       ◦ Here, the topics_root_dir contains one sub-folder per topic; the sub-folder name is the
          topic key.
       ◦ The failure probability specifies how frequently the client-server session is interrupted.
   •   Required invocation of client program
       ◦ ./client <server_ip> <server_port> <topic> <output_dir>
       ◦ The invocation fetches topic and writes files under output_dir/topic/
   • Running make inside each Part1/, Part2_Case1/, Part2_Case2/, Part2_Case2_Enhanced/,
       folder must produce (or update) exactly two executable files in that same folder, named
       “server” and “client”. A wrapper shell script invoking a compiled binary or an interpreter is
       fine, as long as it is named exactly server or client and is directly runnable as per the above
       invocations.
   • Extra optional trailing arguments are allowed for case-specific configuration (e.g., number
       of parallel connections for Case 2 Enhanced), as long as sensible defaults exist so the two
       invocations above, used as-is, always work.
